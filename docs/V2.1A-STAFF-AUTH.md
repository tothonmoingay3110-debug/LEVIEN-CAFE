# V2.1A — Staff authentication and role-based access

V2.1A replaces the shared Admin identity with individual Supabase Auth accounts.
The existing environment-based Admin login remains available as a temporary
Owner fallback so a migration cannot lock the store out of Admin.

## Roles

| Role | Current V2.1A access |
| --- | --- |
| Owner | Full Admin workspace and all reserved workforce permissions |
| Manager | Full Admin workspace and all reserved workforce permissions |
| Supervisor | Operations dashboard and order management |
| Staff | Personal account workspace; scheduling arrives in V2.2 |

`view_compensation` is reserved for Owner and Manager. No compensation or
scheduled-hours fields are included in a Staff session response.

## 1. Apply the database migration

Run the complete contents of:

`supabase/migrations/20260816000100_v2_1a_staff_auth_rbac.sql`

in Supabase Dashboard → SQL Editor.

## 2. Create the first Owner identity

1. Open Supabase Dashboard → Authentication → Users.
2. Choose **Add user** → **Create new user**.
3. Enter the Owner email and a strong password.
4. Enable automatic email confirmation for this manually-created account.
5. Run the following SQL after replacing the email and name:

```sql
insert into public.staff_profiles (auth_user_id, email, full_name, role, active)
select id, email, 'LEVIEN Owner', 'owner'::public.staff_role, true
from auth.users
where lower(email) = lower('owner@example.com')
on conflict (auth_user_id) do update set
  email = excluded.email,
  full_name = excluded.full_name,
  role = excluded.role,
  active = true,
  updated_at = now();
```

The statement should report one inserted or updated row. The Owner can then
sign in at `/admin` using the email and password created in Supabase Auth.

## 3. Add more staff during V2.1A

Create each account in Authentication → Users, then run the same insert with
one of these roles:

- `manager`
- `supervisor`
- `staff`

V2.1B will replace this manual setup with an Owner/Manager employee-management
screen. Until that screen exists, do not enable public user sign-up.

## Security notes

- Role authorization is enforced by every protected Admin API route.
- `staff_profiles` has RLS enabled; authenticated users can only read their own
  active profile directly.
- Profile creation and role changes require the server service role or Supabase
  Dashboard access.
- A deactivated profile cannot open a staff session.
- Orders are no longer persisted inside the Admin localStorage cache.
- Keep `SUPABASE_SERVICE_ROLE_KEY` server-only.

## Legacy Owner fallback

`ADMIN_USERNAME`, `ADMIN_PASSWORD`, and `ADMIN_SESSION_SECRET` continue to work
as a temporary Owner login. Keep them configured until the first Supabase Auth
Owner login has been tested in production. Removing the fallback will be a
separate hardening change after V2.1B.
